3 ОПИС ВИКОНАНОЇ РОБОТИ


3.1 Загальні відомості про систему
Об'єктом дослідження є платформа Trello. Даний продукт, первісно розроблений командою Fog Creek Software, а зараз керований Atlassian, став одним із найвідоміших інструментів для управління проєктами на базі канбан-дошок. Аудиторія сервісу максимально широка, від окремих фрілансерів до відділів у транснаціональних корпораціях. Оскільки щоденно система обробляє мільйони запитів та взаємодій, до її серверної частини висуваються надзвичайно жорсткі вимоги. Йдеться насамперед про стабільну відмовостійкість та мінімально можливі затримки, адже ключова особливість Trello як раз синхронізація робочого простору в реальному часі.
3.2 Архітектурний стиль системи
Архітектура Trello пройшла шлях від початкової монолітної клієнт-серверної моделі до сучасної сервіс-орієнтованої архітектури.
Основним доказом цього переходу є декомпозиція початкового монолітного бекенду на базі Node.js на низку незалежних, вузькоспеціалізованих сервісів. Зокрема, було виокремлено автономні модулі для обробки авторизації, управління дошками та взаємодії із зовнішніми розширеннями. Таке рішення дозволило усунути проблему «єдиної точки відмови» та якраз забезпечило можливість масштабувати окремі частини системи залежно від поточного навантаження.
Паралельно із впровадженням сервісного підходу, ключовим елементом системи стала подієво-орієнтована модель, і вибір цієї моделі є критично важливим для забезпечення головної функціональної вимоги платформи, а саме синхронізації стану дошки між усіма активними клієнтами в реальному часі.
Також замість ресурсомісткого методу постійного опитування сервера, який створює надлишковий мережевий трафік, архітектура Trello базується на миттєвій трансляції подій. Тож будь-яка зміна даних генерує системну подію, яка через брокер повідомлень Redis одразу доставляється всім підключеним користувачам і не треба кожен раз оновлювати сторінку, тощо. Класичний підхід із постійним опитуванням сервера був би невигідним, бо в режимі надмірного навантаження просто б не витримав.
3.3 Основні компоненти системи
Розглянути самі компоненти можна насамперед через призму їхніх завдань, наприклад клієнтська частина реалізована як односторінковий застосунок з використанням бібліотеки React. Тут варто звернути увагу на застосування так званої концепції "оптимістичного UI" (або на англ. «Optimistic UI»). Якщо не вдаватися в подробиці, це доволі хитрий підхід, бо, наприклад, коли ви перетягуєте картку, клієнтський додаток відмальовує її на новій позиції миттєво, ще до того, як серверна частина поверне статус 200 OK. У користувача створюється враження нульової затримки.
Щодо серверної складової, вона реалізована за допомогою платформи Node.js. Вибір цього набору технологій пояснюється асинхронною природою середовища. Завдяки циклу подій лише один сервер здатен підтримувати десятки тисяч активних постійних з'єднань, не витрачаючи оперативну пам'ять на створення нових процесів під кожного клієнта.
Зберігання даних працює на базі MongoDB. Табличні бази для такого проєкту виявилися б занадто обмеженими. Дошка, список, картка з довільною кількістю контрольних списків, все це добре вписується в ієрархію текстових документів формату JSON.
Також критично важливим компонентом є Redis. Він задіяний у режимі «видавець-підписник» (або англ. «Pub/Sub») і виконує роль високошвидкісного посередника передачі повідомлень між серверами Node.js.
3.4 Взаємодія компонентів
Проте важливо розуміти, як саме працює ця структура на практиці. Припустимо, хтось перемістив картку в інший список. У цьому випадку спочатку клієнтська програма формує запит до програмного інтерфейсу (метод PUT), який проходить через розподільник навантаження HAProxy і потрапляє на один із вільних вузлів Node.js. Сервер швидко перевіряє ключ доступу і записує нові координати картки в базу MongoDB.
Одразу після успішної фіксації змін у базі, цей самий сервер публікує повідомлення про подію в певний канал Redis. У цей час інші сервери Node.js, які підписані на цей канал, отримують сповіщення. Вони перевіряють свою пам'ять: чи є у них зараз активні з'єднання з користувачами, що відкрили цю ж саму дошку, і якщо такі клієнти є, сервер миттєво відправляє їм оновлені дані у форматі JSON через постійне з’єднання, і браузери синхронізують зображення на екрані.

3.5 Масштабованість та надійність
Забезпечення стабільної роботи при такому потоку даних вимагає комплексних рішень. Вхідне навантаження розподіляється на рівні HAProxy. А от з базою даних ситуація набагато складніша.
MongoDB розгорнута у вигляді груп серверів (так званих «Replica Set»), де завжди присутній основний вузол і кілька резервних. І при умові, що основний сервер виходить із ладу, система автоматично перемикається на резервний, проте коли обсяг даних став критично великим, розробникам довелося впроваджувати фрагментацію. Тобто дані фізично розбиваються по різних серверах. Ключем горизонтального розподілу даних інженери обрали ідентифікатор дошки/робочого простору. Тобто, уся інформація конкретної компанії завжди зберігається на одному фізичному сегменті, що повністю усуває проблему повільних запитів між різними серверами. Додатково інтенсивно використовується проміжне збереження популярних запитів у швидкій пам'яті, що теж суттєво розвантажує дискову підсистему бази даних.

Також було розглянуто механізми забезпечення відмовостійкості в цьому інструменті, а саме балансування мережевого трафіку, кешування та горизонтальний розподіл даних .

Методологічна довідка (згідно з п. 3.3.2 Положення про використання ШІ в ХНУРЕ):

Назва інструменту та версія: Google Gemini (версія 3.1).
Мета використання: 
1. Пошук та структурування інформації щодо еволюції архітектури платформи Trello;

Внесок автора: усі тези щодо архітектури (Node.js, MongoDB, Redis) були верифіковані автором через аналіз технічного блогу Atlassian Engineering. Приклади використаних запитів (промптів):
* «Проаналізуй архітектурний стек Trello. Чому використання Node.js та асинхронної моделі Event Loop є критичним для їхнього механізму оновлення в реальному часі?»
* «Допомоги з прикладом JavaScript-коду для Trello REST API. Потрібна функція на async/await для створення картки (POST-запит) та отримання списку карток (GET-запит).»
Лістинг В.1 — Створення картки через Trello REST API (POST-запит):
1  async function createNewCard(listId, name, desc, key, token) {
2     const endpoint = `https://api.trello.com/1/cards`;
3     const params = new URLSearchParams({
4          idList: listId, name, desc, key, token
5     });
6  
7     try {
8          const response = await fetch(`${endpoint}?${params}`, {
9              method: 'POST',
10             headers: { 'Accept': 'application/json' }
11         });
12  
13         if (!response.ok) throw new Error(`Помилка: ${response.status}`);
14  
15         const result = await response.json();
16         console.log(`Картку створено з ID: ${result.id}`);
17         return result;
18    } catch (error) {
19         console.error(`Помилка запиту:`, error);
20    }
21 }


Лістинг В.2 — Отримання списку карток (GET-запит):
1  async function getBoardData(boardId, key, token) {
2     const endpoint = `https://api.trello.com/1/boards/${boardId}/cards`;
3     const params = new URLSearchParams({ key, token, fields: 'id,name' });
4  
5     try {
6          const response = await fetch(`${endpoint}?${params}`, { method: 'GET' });
7          if (!response.ok) throw new Error(`Помилка: ${response.status}`);
8  
9          const cards = await response.json();
10         return cards;
11    } catch (error) {
12         console.error(`Помилка отримання даних:`, error);
13    }
14 }
